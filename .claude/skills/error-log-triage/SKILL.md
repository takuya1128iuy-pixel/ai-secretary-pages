# エラー調査のときのログの読みかた

**目的：無駄にクレジット（＝AI の利用料。読んだ文字の量で増える）を使わないこと。**
ログ全文を読み込むのがいちばんの無駄づかいなので、そこを止める。

## 守ること（これだけ）

1. **該当エラーの前後 50 行を確認する。** まず行番号を特定し、その範囲だけを取り出す。
2. **足りないときだけ範囲を広げる。** 50 → 150 → 400 行と段階的に。いきなり全部は開かない。
3. **全文は出力しない。** 自分が読むときも、利用者に見せるときも、抜粋だけ。

## 手順

```bash
# 1. エラーの行番号を探す（本文は出さず、どこにあるかだけ）
grep -n -iE 'error|exception|traceback|failed|fatal' ログのパス | tail -20

# 2. その行（例: 1234 行目）の前後 50 行だけを読む
sed -n '1184,1284p' ログのパス

# 3. それでも原因がわからないときだけ広げる
sed -n '1084,1384p' ログのパス
```

- 行番号がわからない形式のログなら `grep -n -C 50 'エラーの文言' ログのパス` でもよい。
- ログがコマンドの出力なら、そのまま渡さず `2>&1 | tail -100` のように切ってから見る。
- 巨大なファイルに `cat` を使わない。`head` / `tail` / `sed -n` / `grep` を使う。

## 利用者への報告

- 貼るのは**原因だと判断した数行**と、**なぜそう読んだか**。ログの塊を貼らない。
- どのファイルの何行目を見たかを書く（例: `build.log:1234`）。
- 範囲を広げたときは「50 行では足りなかったので 300 行に広げた」と一言添える。

## やってはいけないこと

- ログ全文を読み込む／会話に貼る。
- 「念のため全部見ておく」。念のためが、いちばん高くつく。
- 同じログを何度も読み直す。読んだ範囲と結論は、その場でメモしてから次に進む。
